## 用户试用后的实际目录修复

用户随后在本机上传时遇到“图片未能完整保存”。此前默认测试使用系统临时目录，未覆盖实际数据目录的文件操作差异。

在当前资料目录使用独立 UUID、20×20 像素测试图复现 503；当时 C 盘约有 84 GiB 可用空间。逐步检查确认创建、写入、文件同步均成功，最后同一父目录内的目录重命名返回 `EXDEV`。该目录带 Encrypted 属性，但本次没有证明所有加密目录都存在此行为；结论限于实际目录拒绝重命名，不要求用户关闭加密或放宽权限。

修复改为写入新建且尚未发布的 UUID 目录，原图和预览均完成同步后，才通过 SQLite 事务发布引用。API 必须先查到已提交的引用才能读取附件，因此不需要依赖目录重命名，也不会提前暴露半道题。失败仅清理本次确实创建的目录；原有附件路径和记录保持兼容。

给既有公开 API 测试增加 `KLBOOK_TEST_DATA_PARENT`：将独立临时资料库放在实际数据目录内以复现相同环境，不打开用户数据库。上传测试先观察到 503 而非预期 201；修复后全部六项收集 API 用例通过，包括原图字节、重试、材料缺失和重启读取。材料缺失测试改为移除并按原字节恢复测试附件，避免故障注入本身依赖不受支持的重命名。

最小存储探针也由失败转为成功；独立原生重命名探针仍返回 EXDEV，确认修复解决了已知环境限制。已重启现有本机服务并验证健康状态，保留原账号和资料。

修复后的 `npm run build` 成功；完整回归的 15 个 API 用例（使用实际数据目录下的隔离子目录）与 Edge/Firefox/WebKit 共 15 个浏览器用例全部通过，0 跳过、0 失败。输出保存在本机 `.scratch/attachment-storage-fix-tests.log`。
